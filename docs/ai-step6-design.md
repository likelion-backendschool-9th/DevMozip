# STEP 6A·6B 사전 설계 검토

## 2026-11-10 단계 종료 및 후속 경계

6A와6B는 구현·자동 검증을 마쳤다. 최신 확정은 [6B 구현 계약](ai-portfolio-analysis.md)과 [종료 점검](ai-progress.md#2026-11-10-6b-종료-점검--현재-구현-기준)을 따른다. 실제 Gemini/공유DB 신규API/브라우저 검증은 미완료다. 아래 사전 설계와 준비 기록은 이력이며 신규 작업 지시가 아니다.

확정 변경: 현재 역할과 유효 구독 모두 필수, 공개 메타데이터 관련 최대5개, 근거 설명만 제공, 신규 기본 추천의 실질 관련성 필터, summary 평가 입력, UNKNOWN 표시 숨김/부분 구현 유지, 완료 후 자동조회 중단, 무료 전용 안내·구독 링크, 단일 시안색 별28px. 과거 추천 재계산·본문 가산점·월 사용량·실결제/구독 활성화는 구현하지 않았다.

7단계는 명시 구현 요청 전 시작하지 않는다. 사용량 API/초과 오류·KST월 집계·성공 신규 추천의 원자적 멱등 차감·대화 삭제 후 사용량 유지 계약과 실제 DDL을 먼저 확인한다. “네” 재확인 문제와 기본 추천 장기 PENDING 복구는6B 상세 임대 회복과 구분해 별도 범위를 확정한다.

## 2026-11-09 6B 확정 및 구현

작업 브랜치는 `feat/gemini-portfolio-analysis`. 사용자 최신 결정으로 개발자 추천 결과의 상세 근거만 구현하고 점수/순위 가산은 후속으로 둔다. 공개 메타데이터를 요청 당시 요구와 비교해 관련성 있는 최대5개를 선택한다. 관련 자료 부재 시 개수를 채우지 않으며 선택 이유와 자료를 표시한다. 본문 외 첨부/외부URL은 제외한다.

추가 답변으로 **구독 기록이 없는 PREMIUM도 차단**한다. 현재 DB PREMIUM/ADMIN과 현재 유효 구독을 모두 검사하며 역할만 허용하는 대안은 폐기했다. 구독/회원/포트폴리오 도메인·스키마를 바꾸지 않는 AI 전용 읽기와 기존 detailed_reason CAS 저장으로 구현했다. 무료·만료 차단, 모델 실패/타임아웃, 현재 자료·권한 재검증, 동시 중복/임대 회복을 포함한다. 상세 API/저장/선택 한계는 [구현 계약](ai-portfolio-analysis.md), 실행 결과는 [진행 현황](ai-progress.md) 최신 절이 기준이다. 아래 미확정·미착수는 당시 설계 이력이다.

기준일: 2026-11-09. 최신 6A 구현·권한 제한·부분 충족 50점 확정은 [API 최신 계약](ai-api-spec.md#2026-11-09-step-6a--자연어-요구사항-추천-반영-현재)과 [진행 현황](ai-progress.md)을 우선한다. 아래 사전 설계 기록의 미착수·미확정 표현은 당시 상태다. 현재 상태: **6A·6B 구현 및 자동 검증 완료, 실사용 검증은 일부 미완료**. 아래 사전 설계 기록은 당시 상태이며 현재 구현은 최신 API·진행 문서를 따른다.

사용자 요청으로 종전 6단계를 6A(자연어 세부 요구사항을 실제 추천에 반영)와 6B(프리미엄 포트폴리오 기반 상세 추천 분석)로 분리한다. 아래 사용자 답변으로 명시적으로 확정한 정책 외 추천안·DTO 방향은 승인된 정책이나 구현된 API가 아니다. 정책 확정 후 6A부터 구현하고 완료 후 6B를 자동 시작하지 않는다.

## 선행 설계 당시 확정 정책 — 이력(현행은 상단 참조)

- 허용된 공개 후보 정보를 Gemini에 보내 의미상 부합 근거를 추출하고 서버가 근거를 검증해 최종 점수를 계산한다. 후보별 자료 참조·정확한 인용·요구사항 ID를 받는 별도 평가 계약을 설계하며, 인용 검증은 후보 경험의 진위 인증과 구분한다.
- 무료·프리미엄 모두 개발자와 유사 프로젝트에 적용한다. 본인 보유·학습 기술·수준을 상대에게 요구하는 조건으로 바꾸지 않는다. 참여/모집 목적에 따른 새 필터와 관심 분야 ‘제한 없음’ 실행 정책 변경은 보류한다.
- 세부 요구사항이 있으면 `기존 환산점수 × 0.8 + 요구사항 점수 × 0.2`, 없으면 기존 점수를 유지한다. 선호 점수 방식이며 새 필수 필터는 만들지 않는다. **미확인 요구도 0점으로 분모에 포함**한다. 모든 요구가 미확인이어도 요구사항이 있으면 80:20을 적용한다. 표시에서는 미확인과 불일치를 구분한다.
- 필터 통과 전체 후보를 배치 분석한다. 분석 실패 시 추천 실패로 처리하고 새 성공 결과를 만들지 않는다. 상위 일부만 분석하거나 규칙 점수로 조용히 대체하지 않는다.
- **기존 권한 정책을 변경**하여 무료도 허용된 포트폴리오 본문을 내부 점수 분석에 사용하되 원문·상세 근거를 숨긴다. 프리미엄 전용 6B 상세 분석/열람과 분리한다. 현재 확인한 DB public에는 본문 테이블이 없어 실제 자료 출처·서버 읽기/공개 범위 계약은 남아 있다. 비공개 자료 임의 접근·다른 팀 도메인 생성·Mock 연결까지 승인된 것으로 보지 않는다.
- 선행 요구: 대화 분석에 일부 선택값도 전달하고 추천 버튼에서만 필수 조건의 완성을 검증한다. 사용자 표현 ‘6A 구현 전 작업’에 따라 별도 선행 단계로 구현한다. 누락값에 임의 기본값을 채우지 않으며 전달된 값의 타입·허용값·범위 검사는 유지한다.
- 이번 선행 구현은 기존 sync의 조건을 전체 초안(DraftConditionsRequest)으로 저장하는 계약이다. 생략/빈 목록/null은 선택 해제, facts 보존, 완전 조건 PUT·추천 실행 검증 유지. 프론트 분석 전 sync는 부분 초안도 전달하고 실패 후 분석 재시도에서는 같은 메시지 키로 진행하며 sync하지 않는다. 세부 계약은 [API 문서](ai-api-spec.md#2026-11-09-부분-선택값-전달-선행-계약-현재)를 따른다.
- 6A의 요구사항 스냅샷·재추천/재시도·항목별 부분 부합 계산·기존 프로젝트 텍스트 항목 중복 방지는 후속 구현에서 구체화할 설계다. 이번 선행 단계에 포함하지 않는다. 6B 생성·열람도 별도 미착수다.

## 2. 6A 구조 — 확정 사항 외 세부 설계는 미승인

흐름: 사용자 발언 → 기존 5단계 분석·병합 → 서버에서 추천용 요구사항 정규화 → 실행 시점 스냅샷 → 기존 후보 필터 → 요구사항 대조·점수·기본 이유 → 요청/결과 저장 → 기존 조회.

1. 5단계의 원문 근거·출처를 유지하면서 엔진 전용 입력을 분리한다. `_analysis` 전체를 곧바로 점수 입력으로 사용하지 않는다. suggestions/questions/appliedChanges는 평가 대상이 아니다. EXPLICIT도 모델 분류 결과이므로 원문 인용 일치만으로 의미 해석 정확성까지 보장하지 않는다.
2. 6A 기본 후보 데이터는 허용된 공개 필드를 사용하고, 최신 사용자 답변으로 사용 가능한 포트폴리오 본문도 분석 자료로 포함하는 방향이다. 무료 내부 점수 사용도 승인했으며 본문의 실제 저장소·서비스 읽기 계약은 남아 있다. OWN_SKILL/LEARNING_SKILL/USER_LEVEL은 사용자의 맥락이며 상대 기술·경력으로 전환하지 않는다. TARGET_SKILL은 정형 stacks와 중복 가산하지 않도록 합치거나 역할을 분리해야 한다. TARGET_EXPERIENCE의 경험 증거는 현재 확인한 자료에 없어 미확인으로 남긴다.
3. FEATURE/PROJECT_PREFERENCE는 공개 프로젝트 제목·설명과 대조할 수 있다. COLLABORATION_GOAL/LEARNING_GOAL은 프로젝트 텍스트에 근거가 있는 범위만 대조 가능한 후보이며 개발자의 멘토링 역량을 추정하지 않는다. PURPOSE의 새 후보 필터와 관심 제한 없음 실행 정책은 사용자 답변으로 보류했다. OTHER의 세부 평가 규칙은 후속 설계다. ‘참여’라고 완료 프로젝트를 제외하면 기존 유사 사례 추천 정책이 바뀌므로 별도 결정이 필요하다.
4. 현재 facts에는 필수/선호/제외/무제한을 나타내는 별도 필드가 없다. 단순 키워드 일치로 ‘결제 경험 없어도 됨’, ‘주제 상관없음’을 긍정 요구로 채점하면 안 된다. 부정·완화·정정 표현을 평가 대상에서 분리할 규칙 또는 구조 확장과 재분석 전략이 필요하다.
5. 사용자 확정 방식은 허용된 공개 후보 정보를 Gemini에 보내 근거를 추출한 뒤 서버가 검증·계산하는 방식이다. 무료도 본문을 내부 점수 분석에 사용할 수 있지만 원문·상세 근거는 숨긴다. 실제 자료 계약은 남아 있다. 필터 통과 전체 후보 배치 분석과 분석 실패 시 새 성공 결과를 만들지 않는 정책은 확정했다. 배치 크기·출력 한계·동시 실행 제어는 후속 구현 설계다. 기존 5단계 프롬프트의 후보 접근 금지 역할을 그대로 변경해 혼용하지 않는다.
6. 사용자 확정 배점은 요구사항이 있을 때 `기존 환산점수 × 0.8 + 요구사항 점수 × 0.2`이며 없으면 기존 점수를 유지한다. 미확인도 0점으로 요구사항 점수 분모에 포함하며 모든 요구가 미확인이어도 80:20을 적용한다. 표시에서 미확인과 불일치는 구분한다. 경험 20점을 요구사항 점수로 바꿔 쓰지 않는 설계를 제안한다.
7. 실행 시점의 정규화된 요구사항·근거 참조·스키마/평가 규칙 버전을 기존 conditions JSONB 안에 보존하는 방식을 우선 제안한다. 새 컬럼 없이 가능하지만 JSON 응답 계약·구형 이력 파서·클라이언트 타입 변경이 필요하다. 구형 요청은 세부 요구사항 없음으로 읽고 당시 점수·순위를 유지한다. GET은 재계산하지 않는다.
8. 같은 Idempotency-Key는 동일한 전체 추천 입력을 식별해야 한다. facts 변경을 비교에 포함하고 같은 키의 다른 입력은 409로 구분한다. 응답 유실 재시도는 서버의 원래 스냅샷을 조회·재사용하도록 설계해 그 사이 바뀐 대화의 facts가 섞이지 않게 한다. 새 키와 요구사항 변경을 구분하며, 무관한 대화 한 줄만으로 재추천 허용 여부가 바뀌지 않도록 정규화 입력을 비교한다.
9. 현재 messageId는 원문 범위 기준이고 현재 facts와 별도다. 6A에서는 추천 실행 시점의 확정 요구사항을 기준으로 삼는 방향을 제안하나, 과거 messageId를 지정한 실행에 최신 facts를 섞을지/거절할지 계약이 필요하다. 분석 실패·진행 중에 이전 facts로 조용히 추천하지 않도록 재시도/수동 추천 선택을 명확히 한다.
10. 기존 누적 원문 텍스트 점수와 facts 점수의 중복 반영을 피해야 한다. 프로젝트 기존 텍스트 20점을 정규화된 현재 요구로 대체할지, 별도 요구사항 항목으로 재구성할지 선택한 점수 방식에 맞춰 확정한다. 과거 삭제된 요구와 본인 보유 기술을 원문에서 다시 가산하지 않는다.

6A 변경 후보는 AI 전용 DTO·조건 문서/병합·후보 projection·엔진/계산·실행 서비스, 프론트 AI 타입·API·homeStore·추천 표시와 관련 테스트다. 공개 summary/goal 등 추가 필드 사용이 필요하면 해당 공개 계약을 먼저 확인하고 AI 읽기 projection만 확장한다. 다른 팀원 담당 엔티티·도메인·인증·배포 설정과 Mock 데이터의 DB 이전은 포함하지 않는다.

## 3. 6B 구조 제안과 선행 계약 — 미승인

- 기존 문서 경로 `POST /api/v1/ai/recommendations/{id}/detailed-analysis`는 추천 결과 PK를 사용하며 requestId/사용자 ID와 구분한다. 상세 DTO·오류·재조회 계약은 아직 없다. 기존 기본 추천 응답에 detailed_reason을 무조건 추가하지 않는다.
- 인증된 사용자 → 추천 결과가 속한 대화 소유권 → 현재 서버 프리미엄 자격 → 해당 후보 포트폴리오 열람권을 확인한 뒤 자료를 읽는다. 저장된 분석 재사용 시에도 자격·열람권을 다시 확인한다. ADMIN/OWNER 예외는 확정하지 않았다.
- 선행 필요: 포트폴리오 실제 저장소/읽기 계약·visibility 허용값·기본/상세 필드 경계·외부 AI 전송 허용 범위, 구독 자격 원천·만료 시점. 현재 users.role만 임시 자격으로 사용할지는 별도 승인 사항이다. 관련 도메인을 AI 작업에서 대신 구현하지 않는다.
- 후보 생성·최종 점수/순위는 서버가 결정한다는 기존 정책을 유지한다. 6B는 요청 스냅샷과 허용된 실제 포트폴리오 근거로 상세 설명을 생성하고 기존 점수·순위를 유지하는 방향을 제안한다. 경험 점수 활성화·순위 재계산을 원하면 범위를 별도로 확정한다.
- 분석 내용 제안: 요구별 부합 근거, 부분 부합, 확인 불가, 협업 전 확인 질문. 포트폴리오의 자기서술을 실력 검증 완료로 표현하지 않는다. 자료에 없는 경험·기술·성과를 생성하지 않으며 입력 자료 속 지시문을 실행하지 않는다.
- Gemini 호출은 트랜잭션 밖에서 수행하고 입력 검증·결과 저장을 분리한다. 생성 중 구독·공개 범위·문서가 바뀌면 저장/노출 직전 재검증한다. 동일 결과·자료 버전·분석 버전의 동시 생성 중복 방지, 타임아웃·재시도 계약이 필요하다.
- detailed_reason TEXT 하나만으로는 근거 문서/버전·권한 변경·동시 생성·상태·실패 재시도 정보를 관리하기 어렵다. 구조화 JSON 저장 또는 AI 전용 메타데이터 컬럼/테이블 중 방식을 6B에서 검토하며 DDL을 지금 추가하지 않는다. 요청 단위 analysis_level 하나로 결과별 생성 상태를 표현할 수 없으므로 자동 추가하지 않는다.
- 포트폴리오 수정 시 캐시 무효화/재분석, 삭제·비공개 시 기존 분석 노출 중단/파기, 프리미엄 만료 후 과거 상세 열람, 원문 보존 기간을 확정해야 한다. 기본 추천 점수/순위 스냅샷 보존과 상세 자료의 열람권은 분리한다.
- 상세 분석·재조회는 추천 사용량을 차감하지 않는 기존 정책을 유지한다. 생성 호출 남용 방지와 월 추천 사용량 구현(7단계)은 별개다. 6A 완료 후에도 6B는 별도 착수 요청을 기다린다.

## 2026-11-09 6B 구현 준비 재점검

이번 사용자 요청은 6A 오류 조사·누락 보완과 **6B 준비**다. 상세 분석 생성·본문 AI 전송·새 엔드포인트·구독 도메인은 착수하지 않는다.

### 확보한 실제 계약

- `git fetch origin develop` 결과 `a04608f`; 현 HEAD `abb6585`가 이미 포함한다. 추가 pull/병합할 변경이 없다. 브랜치 `feat/gemini-recommend`를 유지하며 main/커밋/푸시는 수행하지 않는다. 최신 develop 포함 상태에서 검증한다.

- 현재 타인 상세는 **DB의 최신 users.role PREMIUM/ADMIN**, 작성자 ACTIVE, visibility PUBLIC만 허용한다. PRIVATE는 타인 ADMIN도 404다. 본인 ACTIVE/WARNED는 자신의 PUBLIC/PRIVATE를 볼 수 있지만 이를 AI 타인 추천 권한으로 확장하지 않는다. `ProjectPortfolioAccessConfiguration`의 기본 구현은 여전히 unavailable이며 프로젝트 지원용 계약을 AI 본문 읽기 수단으로 사용하지 않는다.

| 비용·동시성 | 지연 생성, 같은 자료/요구 중복 실행 제어, 실패 재시도·유효기간·호출 상한, PENDING 복구. |
| 결과 | 6B는 기존 점수·순위를 보존하는 상세 설명인지 최종 확인. 근거 인용/부분 부합/미확인/확인 질문, 자기서술과 검증된 경험 구분. |
| 검증 | 실제 PostgreSQL 권한·삭제/비공개·구독 만료·캐시 무효화·중복 호출, 실제 Gemini 품질을 격리 테스트와 별도로 확인. |

이전 기록의 본문 테이블·API 부재는 해소됐다. 구독 유효기간·AI 상세 계약과 현재 권한/자료 버전 재검증은 아직 미구현이다. 최신 무료 열람 가능 자료 제한을 유지하므로 현재 프리미엄 전용 본문을 무료 6A에 자동 연결하지 않는다.
