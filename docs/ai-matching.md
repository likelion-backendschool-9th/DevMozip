# AI 추천 공통 기능 정책

## 2026-11-10 월간 추천 잔여 표시

- matching 추천 조건 패널은 무료·프리미엄 모두 서버 `remainingCount / limit`를 ‘월간 추천 잔여’로 표시한다.1회 사용 시 무료4/5회·프리미엄99/100회이며 기존 차감·예약 정책과 API 계약은 유지한다.

## 2026-11-10 메인 첫 프롬프트 분석 연결

- 사용자 요청으로 `feat/ai-prompt`에서 메인 ‘추천 시작’ 및 로그인 후 입력 복원으로 생성된 첫 USER 메시지를 matching 진입 후 기존 메시지 분석 API로 처리한다. 이력 로딩을 마친 새 로컬 대화만 대상으로 하며 기존 서버 대화·미완료 분석은 자동 재실행하지 않는다.
- 처리 중 기존 분석 로딩 표시를 사용하고, 실패 시 오류와 수동 재시도를 제공한다. 같은 화면에서 effect 재실행으로 첫 분석을 중복 요청하지 않는다. 분석 답변·조건 반영은 기존 계약을 사용하며 추천 생성·월 사용량 차감은 별도 추천 버튼 동작을 유지한다. 새 API·외부 AI 연결·백엔드·DDL 변경은 없다.

현재 완료/미완료·변경 파일·최종 검증은 [7단계 종료 점검](ai-progress.md#2026-11-10-step-7-종료-점검--현재-구현-기준)을 우선한다. 무료5/프리미엄100, KST 수신 월, 0건 성공 차감, 실패/조회/상세 미차감, 구독 변경 시 기존 used 유지 정책은 변경하지 않았다. CHAR JDBC 수정은 기존 DB 계약에 맞춘 결함 수정이다. 아래 날짜별 과거 ‘7단계 미구현’은 해당 작업 당시 상태다.

## 2026-11-10 STEP 7 구현 정책

사용자는 무료5회/유효 구독 프리미엄100회, 접수한 KST 월 귀속, 0건 정상 완료 포함 요청당1회, 실패 전체 미차감, 접수 후 구독 변경 시 기존 요청 완료 허용·다음 신규 추천부터 현재 한도 적용에 합의했다. ADMIN 무제한 예외는 없고 구독 변경 시 같은 달 사용 횟수를 초기화하지 않는다. 짧은 DB 잠금과 처리 중 예약으로 동시 초과 실행을 제어한다. API 필드는 usageMonth/usedCount/limit/remainingCount/pendingCount/availableCount이며 자리 부족은429·AI_MONTHLY_LIMIT_EXCEEDED로 구별한다.

API·ERD·트랜잭션은 [7단계 구현 계약](ai-usage-api.md), 실제 학습/트러블슈팅은 [설계 기록](ai-step7-concurrency-notes.md)을 따른다. 기본30분 예약, 조회/실행 시 만료 회복을 구현했다. 이후 사용자가 공유 SQL을 적용했고 에이전트는 테이블·컬럼·주요 제약을 읽기 전용으로 확인했다. 기동 중 CHAR(7) 검증 오류는 엔티티 JDBC 매핑 누락을 수정했다. 에이전트의 공유 DDL 실행·배포는 없으며 아래 미구현 설명은 당시 이력이다.

## 2026-11-10 6B 종료 기준 — 최신 정책

6B 상세 분석과 자동 검증을 구현했다. 운영/실제 Gemini·브라우저 검증 완료를 뜻하지 않는다. 상세 구현·한계는 [6B 계약](ai-portfolio-analysis.md), 변경 파일·실행 기록은 [6B 종료 점검](ai-progress.md#2026-11-10-6b-종료-점검--현재-구현-기준)을 따른다. 아래 날짜별 미착수·미확정·이전 UI 기록은 당시 상태다.

- 현재 DB PREMIUM/ADMIN + 유효 구독 기록을 모두 요구한다. 구독 없는 데모 프리미엄/ADMIN 우회는 없다. 무료 버튼은 클릭 시 API 없이 전용 안내·구독 페이지 링크를 제공하고, 최종 장식은 시안색 단일 별28px다. 구독 페이지는 프로토타입이며 실제 구독을 생성하지 않는다.
- 공개 메타데이터와 요청 스냅샷으로 관련 최대5개 본문을 선택한다. 작성자의 자기서술을 정확 인용으로 제시하며 검증된 실력으로 보장하지 않는다. 현재는 근거 설명만 제공하고 본문 가산점/순위/사용량 차감은 하지 않는다.
- UNKNOWN·NO_DATA는 화면에서 숨기며 PARTIAL/구현 중/명시 차이는 유지한다. 이 표시 정책과 별도로 신규 기본 추천은 아래 확정된 관련성 기준을 적용한다. 기존80:20·UNKNOWN 분모와 과거 저장 결과는 유지한다.
- 완료 상세의 반복/포커스 자동조회는 없다. PENDING에서만3초 간격 최대60회 GET하며 다음 명시 요청에서 현재 권한/자료를 재검증한다.
- 프로젝트 summary 평가 입력은 연결 완료다. 짧은 “네”로 기술 추가 확인을 반복하는 대화 문제는 해결 완료에 포함하지 않는다. 월 사용량은7단계 미구현이며 다음 단계는 별도 지시 후 시작한다.

## 2026-11-10 6B 프리미엄 전용 안내

- 무료 사용자도 ‘포트폴리오 추천 이유 보기’ 버튼을 표시한다. 클릭 시 상세 분석 API를 호출하지 않고 ‘이 기능은 프리미엄 전용입니다.’와 ‘프리미엄 페이지로 이동 →’ 링크(`/subscription`)를 표시한다. 닫기로 안내를 접을 수 있다.
- PREMIUM/ADMIN 화면에서 서버가403을 반환하면 유효 구독 확인 안내와 같은 링크를 표시한다. 그 외 오류는 기존 오류 안내를 유지한다. 서버 권한·구독 검증과 추천 점수·사용량은 변경하지 않는다. 구독 활성화·결제·사용량 구현은 후속 범위다.

## 2026-11-10 요청 관련성 없는 후보 제외 확정

- 최신 사용자 요청으로 새 추천에서 협업 가능·경력·신뢰온도만 충족하는 개발자를 제외한다. 요청 직군 또는 기술 일치가 있거나, 공개 자료의 정확한 인용으로 검증된 세부 요구 MET/PARTIAL 근거가 있으면 유지한다. 신뢰온도·경력만의 세부 평가는 관련성 근거로 사용하지 않는다. 개발자의 관심 분야만 같은 경우도 기술·직군·세부 요구의 연결을 대신하지 않는다.
- 유사 프로젝트는 요청 분야·기술·기존 텍스트 비교 중 하나가 일치하거나 검증된 세부 요구 MET/PARTIAL이면 유지한다. 모집·진행 상태만으로 남기지 않는다. 구현 중·부분 부합·완료 상태라는 이유로 제외하지 않는다. MISMATCH/UNKNOWN만 있고 다른 관련성 근거가 없으면 제외한다.
- 고정 점수 하한은 없다. 기존 공개/계정/협업/직군/경력 필터 다음에 전체 후보의 세부 요구를 평가하고, 관련성을 확인한 후 상위10개를 정한다. 빈자리는 무관한 후보로 채우지 않는다. 기존 점수식80:20과 UNKNOWN 분모는 유지하며 과거 저장 결과·GET·동일 키 재조회는 재계산하지 않는다. 6B 포트폴리오 본문은 여전히 가산점/순위에 미반영이다.
- 기존 도메인·DDL·API 응답 필드는 변경하지 않는다. 아래 관련성/최소점수 미확정 또는 후보 제외 없음 기록은 이 확정 전 이력이다.

## 2026-11-10 프로젝트 한줄 소개 평가 입력 연결

- 사용자 요청으로 프로젝트의 공개 한줄 소개(summary)를 기존 제목/본문/기술과 함께6A 세부 요구사항 평가 자료로 추가했다. 공개·미삭제 프로젝트만 읽고, 기존 개인정보 패턴 마스킹/HTML제거/필드3000자 제한과 정확 출처·인용 검증을 재사용한다. 기존 프로젝트/회원 도메인·테이블 구조는 수정하지 않는다.
- 요약에만 있는 ‘개발자들이 함께 공부하는 스터디 커뮤니티’도 서비스 주제 요구의 근거로 비교할 수 있다. 계획/구현중은 완료 경험과 구분하도록 평가 지침을 보완했다. 같은 요구는 출처가 여러 개여도 한 번만 채점하며 기존 기본80%+요구20%·UNKNOWN0점 분모 정책을 유지한다. 요약을 별도 가산점으로 더하지 않는다. 세부 요구가 없을 때의 기존 원문 텍스트 점수는 바꾸지 않았다.
- 새 추천부터 적용한다. 과거 점수/이유/순위·동일 키 재조회는 재계산하지 않는다. 직전 절의 summary 미전달 설명은 수정 전 상태다.
- 사용자는0점/2.52점 등 낮은 점수 후보 제외에 대한 의견을 요청했다. 현재 협업 가능·경력은 필터이고 점수가 아니며 신뢰온도만으로도 작은 점수가 생길 수 있다. 실질 관련성 기준/최소 점수는 아직 확정되지 않아 이번에 새 탈락 필터를 추가하지 않는다.

## 2026-11-10 추천 설명·상세 분석 조회 UX 보완

- 사용자 요청으로 완료된 상세 분석의30초 자동조회·포커스/탭 복귀 자동조회를 제거했다. PENDING에서만3초 간격 GET을 하며 완료/자료없음/오류/취소 시 중단한다. 최대60회 대기 후 명시 재확인을 안내하고 자동 POST 재시도는 하지 않는다. 서버는 모든 명시 요청/생성중 GET에서 기존 권한·구독·자료 검사를 유지한다.
- 자료 부족 UNKNOWN은 추천 카드·포트폴리오 상세 설명에서 표시하지 않는다. 빈 평가표·NO_DATA 설명·UNKNOWN에서 생성된 확인 질문도 숨긴다. 후보·저장 평가·20%점수 정책은 변경하지 않는다. 실제 구현 중이라는 인용·PARTIAL·명시 차이 MISMATCH는 유지한다.
- 6B는 검증된 인용을 출처 포트폴리오별로 묶어 현재 개발자 이름과 연결한 설명 문장으로 표시한다. 중복 기술 JSON/같은 인용은 합치고 포트폴리오 제목을 기존 상세 링크로 연결한다. 관련 메타데이터 나열 대신 사용 근거를 먼저 보여 주고 자료 선택 원칙은 접어서 제공한다. 추가 Gemini 호출/자유 생성/검증된 성과 주장은 없다.
- 6A의 긴 요구사항별 평가/점수 분해 표시는 근거 있는 짧은 설명으로 교체하고, 모두 UNKNOWN이면 평가 박스 자체를 숨긴다. 프로젝트 진행 상태는 한국어로 유지한다. 현재 프로젝트 평가가 제목/본문/기술만 받고 카드 한줄 요약(summary)은 받지 않는 차이는 확인했으며 이번 표시 수정에서 평가 입력·과거 점수는 변경하지 않았다.

## 2026-11-09 6A 재검증·6B 준비

- 요청 #36의 개발자 0건은 서버 장애가 아니라 실제 선택 직군(게임·모바일·UI/UX)에 맞는 공개·ACTIVE·AVAILABLE 후보 부재다. 같은 DB의 #29~32는 개발자 3건, #33~35는 6건이며 프로젝트는 각 9건이다. 관심 분야·기술·세부 요구사항은 후보 탈락 필터가 아니며 직군/경력/공개·협업 가능 조건을 임의 완화하지 않는다. 빈 결과 화면은 실제 탈락 조건을 안내한다.
- 자연어 요구사항의 80:20 계산·저장은 이미 구현돼 있다. 신뢰온도 선호는 PROJECT_PREFERENCE로 보존하되 개발자 후보의 공개 `trustScore`가 평가 입력에 빠져 있었으므로 추가했다. 현재 숫자와 비교 연산은 Gemini가 분류하고 서버가 해당 후보의 정확 인용과 점수를 검증한다. 신뢰온도를 구현 경험의 증거로 사용하지 않는다. 별도 최소 온도 필터는 추가하지 않는다. 새 추천부터 적용하며 과거 UNKNOWN 결과를 다시 쓰지 않는다.
- 과거 점수·순위·요구별 평가·조건 스냅샷은 GET/replay에서 유지된다. 현재 공개 프로필의 닉네임·기술·온도·협업 상태 등은 최신 값으로 표시하므로 카드 일부가 변할 수 있다. 같은 조건의 신규 요청은 현재 DB와 모델 분류를 사용하므로 과거와 같은 점수를 보장하지 않는다.
- 최신 develop `a04608f`는 이미 현 브랜치 HEAD의 조상이다(fetch로 확인). 포트폴리오 조회 API/본문은 구현돼 있고 실제 DB에는 PUBLIC 1건·PRIVATE 2건이 있다. AI는 여전히 본문을 사용하지 않는다. 아래 과거의 본문 저장소/API 부재 기록은 병합 전 상태다. 6B 준비와 미확정 계약은 [설계 검토](ai-step6-design.md#2026-11-09-6b-구현-준비-재점검)를 따른다. 6B·사용량은 이번에 구현하지 않는다.

- 2026-11-09 최신 develop 통합: 실제 DB 프로젝트 추천은 숫자 ID의 `/projects/{id}`를 최신 `ApiProjectDetail`로 연결한다. Mock ON에서도 숫자 ID는 API 화면을 사용하며 문자열 Mock ID는 기존 화면을 유지한다. AI 전용 간이 상세 페이지는 제거했다. UUID로 만든 브라우저 공고와 DB 공고를 제목으로 대응시키지 않는다. develop의 포트폴리오 조회 구현도 병합됐으나 AI 본문 평가·6B 연결은 이번 범위 밖이며 착수 전 최신 계약을 재확인한다.

- 2026-11-09 표시 순서 보완: 추천에 연결된 USER 메시지 뒤의 저장된 분석 답변을 먼저 보여 주고 추천 결과를 배치한다. 다음 USER의 답변이나 추천 요청 이후 생성된 답변은 이전 결과 앞으로 옮기지 않는다. 추가 AI 호출 없이 화면 정렬만 변경한다.

- 2026-11-09 요구사항 확인 UX: 미전송 입력은 분석/추천 대상이 아니다. 입력이 남은 새 추천은 먼저 전송·분석하도록 안내하고 요청하지 않는다(기존 요청 복구는 당시 입력을 유지). 분석으로 실제 평가 대상 요구가 바뀌면 서버가 저장된 요구사항·다음 추천 평가 예정·미확인 가능성·과거 결과 유지 안내를 답변에 덧붙인다. 본인 기술·추론·면제 요구 등은 기존 평가 추출 규칙을 그대로 따른다. 최소 점수 제외 기준은 없으며 0점 후보 노출과 요구사항 평가 미적용은 별개다. 포트폴리오 본문은 아직 추천 입력에 포함되지 않는다.

- 2026-11-09 조건 요약 중복 보완: 관심 분야·기술·직군·경력·기간은 메시지의 모든 변경을 적용한 후 최종값을 항목별 한 번만 요약한다. 최종값이 이전과 같으면 표시하지 않는다. Gemini 본문은 짧은 대화로 유지하고 반영 조건 열거는 서버 요약에 맡긴다. 추가 모델 호출은 없다.

## 2026-11-09 대화·프로젝트 이동 보완

- 직군별 인원 질문은 모델 질문·서버 보완 질문·답변 본문에 중복 노출하지 않는다. 모델이 직군 인원을 이미 물었다면 서버 질문을 추가하지 않고, 본문에 포함된 동일 질문은 확인 목록에서 다시 출력하지 않는다. 프롬프트도 질문을 questions에 한 번만 작성하도록 안내한다.
- 실제 프로젝트 추천의 상세 보기는 `/projects/{실제 프로젝트 ID}`로 이동한다. 숫자 ID의 상세 화면은 기존 공개 프로젝트 조회를 재사용하고 로딩·조회 실패를 표시한다. 기존 Mock 상세 페이지는 문자열 ID로 유지한다. 프로젝트 백엔드·지원/모집 도메인은 확장하지 않는다.

- 2026-11-09 대화 보완: 직군은 명시했지만 인원이 없는 경우 분석 오류로 중단하지 않는다. 해당 직군을 인원 미정 사실로 보존하고 AI 응답에서 원하는 인원을 질문한다. 인원이 확인될 때까지 기존 정형 직군 조건은 유지하며 임의 기본 인원을 넣지 않는다. 답변 후 확인된 조건을 반영하고 해당 인원 미정 사실을 정리한다.

## 2026-11-09 STEP 6A 현재 정책·구현

- 사용자 구현 요청에 따라 자연어 요구사항을 실제 공개 후보와 비교해 점수에 반영한다. 부분 UI 조건 전달 선행 구현은 유지한다. 일반 대화는 추천·사용량을 자동 실행하지 않는다.
- 기존 필터를 통과한 전체 후보를 Gemini로 배치 비교하고 서버가 출처·인용·ID를 검증한다. 명시 요구만 평가하며 본인 기술·수준·추론·PURPOSE는 보존하되 대상 능력이나 새 후보 필터로 바꾸지 않는다.
- 사용자 확정: 요구별 충족100/부분50/미확인0/불일치0 동일 비중 평균, 요구가 있으면 기본80%+요구20%, 없으면 기본 점수 유지. 필수 표현은 보존·표시하되 별도 승인 없는 후보 탈락은 하지 않는다. 미확인과 경험 부재는 다르다. 전체 분석 실패는 FAILED이며 기본 결과로 대체하지 않는다.
- 실행 시점 정형 조건·facts·출처를 요청 JSONB에 고정하고 기본 점수·요구 충족도·최종 점수·상태를 분리 저장·표시한다. 과거 조회는 재계산하지 않는다. 같은 키 replay로 현재 대화 변경과 분리해 응답 유실을 복구한다.
- **최신 권한 제한**: 무료 평가에는 공개·열람 가능한 정보만 사용한다. 이는 앞선 무료 포트폴리오 본문 내부 활용 허용을 제한하는 최신 요청이다. 이번 구현은 무료/프리미엄 모두 기존 공개 projection만 사용하며 비공개·프리미엄 자료를 조회/전송하지 않는다. 본문 저장소·읽기/열람권 계약이 없어 Mock이나 새 도메인으로 대체하지 않는다.
- 6B 상세 이유·현재 권한/구독/포트폴리오 버전 재검증과 캐시는 별도 미구현이다. 기존 detailed_reason은 생성·노출하지 않는다. 사용량 기능·공통 회원/프로젝트/인증/배포 설정은 변경하지 않는다.
- 세부 제한·저장 형식·배치 비용·기존 프로젝트 텍스트 항목 처리·API는 [6A 계약](ai-api-spec.md#2026-11-09-step-6a--자연어-요구사항-추천-반영-현재), 실행 검증 결과는 [진행 현황](ai-progress.md)을 따른다. 아래 미구현·미확정 설명은 당시 이력이며 최신 절이 우선한다.

## 2026-11-09 부분 선택값 전달 선행 작업·6A 확정 정책

사용자 요청으로 종전 6단계를 **6A 자연어 세부 요구사항의 실제 추천 반영**, **6B 프리미엄 포트폴리오 기반 상세 분석**으로 분리했다. 이번 구현은 6A 전 선행 작업인 부분 선택값 전달만 수행한다. 6A 본체·6B·7단계는 자동 시작하지 않는다. [설계·확정 답변](ai-step6-design.md)을 참조한다.

- 선행 구현: 기존 sync가 빈/부분 조건 초안을 전체 교체로 저장하며, 일반 대화 분석 전에 일부 선택값도 전송한다. 필수값이 없다는 이유로 대화를 차단하지 않고 임의 기본값을 넣지 않는다. 선택한 값의 타입·허용값·범위 검사는 유지한다. 추천 버튼과 서버 추천 실행에서만 추천에 필요한 관심 분야·경력·기간 완성을 검증한다. 기존 완전 조건 PUT 계약은 유지한다.
- 빈/생략/null인 초안 항목은 선택 해제다. 기존 `_analysis.facts`는 보존한다. 분석 실패 후 같은 메시지 재시도에서는 sync를 다시 실행하지 않아 최초 저장한 초안·메시지 키를 유지한다. 기존 추천 엔진·점수·이력·사용량 동작은 변경하지 않았다.
- **6A 확정·미구현**: 무료·프리미엄 모두 개발자와 유사 프로젝트에 적용한다. 허용된 공개 후보 정보를 Gemini에 보내 의미상 부합 근거를 추출하고 서버 검증 후 점수를 계산한다. 본인 보유·학습 기술·수준을 상대 조건으로 바꾸지 않는다. 참여/모집 목적에 따른 새 필터와 관심 분야 ‘제한 없음’ 실행 정책 변경은 보류한다.
- **6A 확정·미구현**: 세부 요구사항이 있으면 기존 환산점수 80% + 요구사항 점수 20%, 없으면 기존 점수를 유지한다. 미확인 요구도 0점으로 분모에 포함하며, 요구가 모두 미확인이어도 요구사항이 있으면 80:20을 적용한다. 미확인과 불일치 표시는 구분한다. 필터 통과 전체 후보를 배치 분석하며 분석 실패 시 추천을 실패 처리하고 새 성공 결과를 만들지 않는다.
- **기존 권한 정책 변경·6A 미구현**: 무료도 허용된 포트폴리오 본문을 내부 점수 분석에 사용하되 원문·상세 근거를 무료 응답에 노출하지 않는다. 6B 프리미엄 상세 분석과 구분한다. 이는 모든 비공개 자료를 임의 조회할 권한이나 다른 도메인 구현 승인이 아니다. 현재 확인한 DB public에는 본문 테이블이 없어 실제 자료 출처·서비스 읽기/공개 범위 계약은 남아 있다. Mock 자료로 대체하지 않는다.

## 2026-11-09 STEP 5 최신 정책

- 사용자 STEP 5 요청으로 Gemini 연결을 승인했다. 최초에는 백엔드 API·테스트만 구현했고, 후속 사용자 요청으로 프론트/BFF 분석 연동과 재시도 보완까지 구현했다. 6단계 포트폴리오 분석·점수 고도화·7단계 사용량은 포함하지 않는다. 아래 과거의 Gemini 미구현·USER 저장 전용 설명은 분석 모드 이전 기록이다.
- 기존 메시지 POST에서 `analyze:true`와 clientKey를 명시하면 자연어 분석을 수행한다. 생략/false는 종전 USER 저장만 수행한다. 분석 모드만 추천 전 서버 저장을 허용하며 기존 프론트의 추천 시 sync 흐름은 바꾸지 않는다. 분석으로 추천을 실행하거나 사용량을 차감하지 않는다.
- 사용자의 보유 기술·학습 기술·수준과 상대에게 요구하는 기술·경험을 분리한다. 목적(참여/모집), 기능, 협업/학습 목표, 프로젝트 선호·기타 요구사항을 보존한다. 정형 조건에 없는 내용이나 관심 제한 없음도 버리지 않는다.
- 기존 조건 키·엔진을 유지하고 current_conditions의 `_analysis`에 세부 요구사항·출처·근거·미확정 제안·질문을 저장한다. 새 테이블/컬럼은 없다. 실제 개발 DB의 해당 컬럼은 JSONB임을 읽기 전용 조회로 확인했다. 원본 ERD 이미지는 이번에 확보하지 못해 저장소 전사와 비교했다.
- 추론 조건은 확정하지 않는다. 수동 선택과 다른 서술은 질문으로 남기며, 명시적인 추가/변경/삭제 명령은 반영한다. 미명시 인원·경력·기간을 채우지 않는다. 2026-11-09 사용자 최종 답변으로 일반 AI 대화는 필수 조건 없이 허용한다. 누락만을 이유로 매번 필수 질문 목록을 덧붙이지 않으며, 추천 준비 대화에서는 AI가 자연스럽게 보완 질문을 할 수 있다. 추천 준비 상태는 선택 여부를 나타내는 참고값이며 대화를 차단하지 않는다. 실제 추천 실행 시 기존 필수 DTO로 검증하고 누락 항목만 질문형 오류 안내로 반환한다. ‘주제 상관없음’은 PROJECT_PREFERENCE로 보존하고 관심 분야를 임의 지정하지 않는다. 새 ‘제한 없음’ 엔진 필터를 만들지 않는다.
- USER를 먼저 저장하고 Gemini 호출은 트랜잭션 밖에서 수행한다. 검증 후 조건과 ASSISTANT를 함께 저장한다. 실패 시 조건을 유지하고 같은 메시지 키 재시도를 지원한다. 분석 도중 바뀐 조건/문맥을 오래된 응답으로 덮어쓰지 않는다.
- PUT/sync는 기존 정형 조건을 교체하면서 세부 요구사항을 보존한다. 추천 엔진/추천 조건 스냅샷에는 종전 정형 조건만 전달한다. 세부 요구사항을 추천 점수에 반영하지 않는다. 6단계의 요구사항 스냅샷/열람권 계약은 추가 구현하지 않는다.
- 무료 지원 기본 모델은 공식 문서에서 확인한 `gemini-3.5-flash-lite`다. 환경변수 키·모델·타임아웃·출력량 설정, 구조화 JSON Schema/DTO 검증, 429/장애/타임아웃 처리를 적용한다. 자동 유료 전환·모델 대체·재시도는 없다. 키 발급 형식을 추측해 점 포함 키를 차단하지 않으며 HTTP 헤더 안전성만 검사한다. 설정 오류는 키·모델·시간·토큰 항목별로 안내한다. Google 거절 응답은 인증/권한/모델/요청/장애를 구분하고 HTTP 상태·허용된 표준 오류 코드와 허용된 field 경로만 제공하며 원문 오류·키·대화 내용은 노출하지 않는다. Google로 보내는 `responseJsonSchema`에서는 공식 안내의 스키마 복잡도 예산을 피하기 위해 배열·수치 한계를 제거하고, 앱에서 동일 한계를 검증한다. 세부 API·설정·한계는 [5단계 API 계약](ai-api-spec.md#2026-11-09-step-5--자연어-분석-api-최신-계약)을 따른다.
- 사용자가 Postman에서 실제 Gemini 분석 성공을 확인했다. 이번 에이전트는 키 없이 외부 호출을 재실행하지 않았으며 무료 프로젝트 할당량·전체 대화 품질 검증을 대신하지 않는다. 가짜 응답 기반 테스트와 실제 외부 호출 검증을 구분한다.
- 최신 인수인계 상태: Cursor가 전송용 wireSchema 단순화·앱의 전체 검증 유지·허용 fieldViolations 안내·비교 진단 스크립트를 반영했다. 사용자 전달 자동 검증은 백엔드 437개 중 436개 통과·1개 스킵, Gemini 호출부 15개 통과다. 후속 사용자 확인으로 Postman의 실제 Gemini 분석 성공을 기록했다. 400 원인의 단독 확정이나 이번 브라우저 연동 검증을 의미하지 않는다. 원본 스키마 400/단순화 스키마 200 비교 후 실제 analyze 응답·저장까지 확인하는 순서는 [진행 현황](ai-progress.md#재확인-순서와-완료-판단)을 따른다.

기준일: 2026-11-09. 전체 단계·현재 완료 범위·남은 요구사항은 [개발 청사진](ai-progress.md), 서버 요청/응답은 [API 명세](ai-api-spec.md)를 따른다. 1~4단계와 5단계 백엔드 분석 API·`/ai/matching` 전송 연동을 구현했다. 6~7단계는 미구현이다. 실제 Gemini 호출은 사용자 Postman 확인 기록과 에이전트 검증을 구분한다. 아래 날짜별 절의 미구현 서술은 당시 기록이다.

## 대화·입력·인증

- 화면은 `/ai/matching`, 서버 기본 경로는 `/api/v1/ai`다.
- 2026-11-07 UI/UX 개선 요청으로 `/ai/matching`의 환영 화면과 입력은 비로그인도 열 수 있다. 서버 대화 조회·저장·추천 실행은 계속 로그인 필수다. 다른 보호 경로와 백엔드 인증은 유지한다.
- 비로그인 메인/AI 입력은 컴포넌트 메모리에서 유지한다. 명시적인 추천 시작·메시지 전송 때만 최대 1500자의 입력을 같은 탭 sessionStorage의 `devmozip:matching-login-prompt:v1`에 10분간 일회성 보관한다. next URL에는 텍스트 없이 resume 토큰만 전달하며 로그인 후 해당 토큰으로 실제 로그인 계정의 로컬 USER 메시지를 한 번 생성한다. 계정 저장 성공 후 인계 데이터를 지우며 실패하면 입력을 보존한다. 서버 저장·자동 추천은 실행하지 않는다.
- guest 대화 자체는 생성·저장하지 않는다. 기존 guest 기록·소유자 없는 과거 메인 입력은 복원/인계하지 않으며, 이번 로그인 동작에 명시적으로 연결된 일회성 입력만 인계한다. 이 변경은 최신 UI 요청의 “로그인 전 프롬프트를 로그인 후 메시지에 반영” 요구를 근거로 이전 입력 미인계 정책을 대체한다.
- 로그인 사용자도 추천 전까지 계정별 로컬 대화·메시지·조건을 사용한다. 메인 입력은 소유 계정이 일치할 때만 복원한다. 로그아웃 후 로컬 변경을 차단하며 서버 영속 API의 인증·소유권 검증을 유지한다. 추천 버튼을 누른 대화만 메시지·조건을 동기화한 뒤 추천한다. 저장 후의 변경도 다음 추천 시 반영하며, 로그인 직후 기존 초안을 일괄 전송하지 않는다.
- 요청자의 신원은 Spring Security 인증 정보에서 얻는다. 본문·쿼리의 userId, 프론트 Mock 계정 ID로 신원을 결정하지 않는다. 익명 추천 실행은 401이다.
- 이메일 기반 JWT 인증을 AI의 `CurrentUserProvider`에 연결했다. 기본/local/운영 환경은 검증된 인증 정보의 이메일로 기존 `MemberRepository.findByEmail`을 호출해 실제 users PK를 얻는다. 익명·미인증·삭제된 사용자는 401, 정지 계정은 403이다. 명시적으로 켠 dev/test 고정 ID는 개발용이며 실제 다중 사용자 인증을 대체하지 않는다.

## 대화·메시지 저장

- 대화는 `createdAt DESC, id DESC`, 메시지는 `createdAt ASC, id ASC`로 정렬한다.
- 메시지 역할은 USER/ASSISTANT다. `analyze`를 생략하면 USER 저장만 한다. `analyze:true`는 5단계 분석으로 ASSISTANT와 조건을 저장하며 추천은 실행하지 않는다.
- 대화 `type/status`는 사용하지 않는다. 한 대화에서 개발자·유사 프로젝트를 함께 추천하며 MVP의 종료/보관 상태는 없다. 실제 DB 컬럼 삭제는 별도 검토 대상이다.
- 조건은 본인만 조회·수정하며 타 사용자·관리자에게 공개하지 않는다. 공개/공유 AI 조건 API는 없다.
- 4단계부터 본인 대화의 추천 결과 → 추천 요청 → 메시지 → 대화를 한 트랜잭션에서 물리 삭제한다. 월 사용량은 삭제·차감·복원하지 않는다. FK 충돌은 전체 롤백한다.
- 서비스가 삭제 순서를 보장하며 신규 추천 FK는 NO ACTION이다. 추천 대상 사용자/프로젝트의 물리 삭제는 참조 이력이 있으면 차단한다. 사용자 탈퇴·개별 메시지 삭제의 후속 처리 정책은 미확정이다. 소프트 삭제는 추천 이력을 삭제하지 않는다.
- AI 시간 필드는 LocalDateTime이다. 앱/DB 기준 시간대는 미확정이며 아래 월 사용량의 한국 시간 규칙과 구분한다.
- 설계 문서의 시간 컬럼 표기는 DATETIME으로 통일한다. 실제 DB별 SQL 타입과 기존 DDL 변경은 별도 구현 범위다.

|---|---|
| 직접 조건 선택 | 2단계 서버 PUT 전체 교체 구현. 분야를 interests로 통합해 1개 이상·경력·기간 필수, 기술·직군 선택. 관심 분야는 기존 5개+분야 7개 선택지, 직군은 직접 입력 허용. 초기 대화/NULL 조회 `{}` 허용, 빈 PUT은 400, 관심 분야·기술은 복수, 직군별 인원은 1명 이상 정수. 상세 DTO·임시 허용값은 API 명세 참조. 프론트는 추천 시 sync에서 동일 DTO로 전달 |
| 추천 실행 | 버튼으로 명시적으로 실행. 실제 DB의 개발자·유사 프로젝트를 한 요청에서 함께 추천 |
| 계산 | 3단계 백엔드 규칙 기반 엔진, 0~100점·점수 내림차순·기본 이유. 2026-11-06 확정 정책은 아래 절 참조 |
| 기본 추천 정보 | 공개 프로필·공개 기술·허용된 기본 경험 등만 사용. 상세 포트폴리오는 사용하지 않음 |

| 요청 조건 보존 | 추천 요청의 conditions는 실행 시점의 변경 불가 스냅샷. 이후 대화 조건 변경과 분리 |

Gemini 연결은 별도 명시적 요청을 받은 단계에서만 한다. API 키는 환경변수로 관리하고 불필요한 개인정보·상세 포트폴리오를 일반 조건 분석에 보내지 않는다. 모델·타임아웃·실패 처리·세부 병합 규칙은 5단계에서 결정한다.

### 3단계 추천 엔진 정책 (2026-11-06)

사용자가 이전 제안 중 별도 변경하지 않은 방향을 승인하고 협업·경력·반환 개수를 수정한 내용을 반영한다. 이후 사용자 구현 요청으로 백엔드 내부 엔진만 구현했다. 외부 실행 API·프론트 연결·결과 저장은 추가하지 않는다.

| 항목 | 적용 정책 |
|---|---|
| 후보·정보 범위 | 실제 DB의 공개 프로필·공개 기술·관심 분야·경력과 허용된 기본 포트폴리오 정보만 사용한다. 본인·정지 계정은 제외하고 기존 공개 조회 조건을 따른다. 상세 포트폴리오는 사용하지 않는다. |
| 모집 직군 | 직접 선택한 직군이 있으면 해당 직군만 추천하고, 미선택이면 전체 직군을 대상으로 한다. 명시적 별칭만 매핑하고 알 수 없는 자유 입력 직군은 추론하지 않는다. |
| 협업 가능 상태 | `AVAILABLE`만 후보에 포함한다. `OPEN_TO_OFFERS`·`RESTING`·`BUSY`·`UNAVAILABLE`·NULL은 제외한다. 협업 상태는 필터이며 점수를 부여하지 않는다. |
| 경력 | 필수 필터다. 경력 무관은 신입·경력 미확인도 포함해 경력으로 제외하지 않는다. `N년 차`/`N년차`와 `N년 이상`을 비교 시 숫자 N으로 정규화한다. 예: 3년 차는 3년 이상 조건을 통과한다. 신입은 0년이며, 최소 연차가 있는 경우 해석 불가·누락 경력은 조건 충족을 확인할 수 없어 제외한다. 경력 자체에는 가산점이 없다. 저장 문자열·공통 Enum을 변경하지 않는다. |
| 개발자 배점 | 직군 30·기술 30·경험 20·신뢰 온도 10을 초기 배점으로 분리 관리한다. 종전 협업 10점은 제거하고 후기는 평가에서 제외한다. |
| 경험 미산정·환산 | **포트폴리오 연동 전에는 경험 20점을 ‘미산정’으로 표시하고, 사용 가능한 평가 항목만 100점으로 환산한다.** 직군·기술을 모두 선택했다면 분모는 70점이다. 미선택 직군·기술도 분모에서 제외한다. 후보자 정보 누락은 선택 조건 미지정과 구분하여 해당 항목 0점으로 처리한다. 포트폴리오 연동 후에는 포트폴리오가 없는 후보자의 경험 가산점을 0점으로 처리한다. 참여 이력·경력을 포트폴리오 경험으로 임의 대체하지 않는다. |
| 신뢰 온도 | 기본 기준은 36.5도다. 36.5도 이하 0점, 이후 선형 증가하여 상한에서 10점으로 제한하는 방향이다. 누락값은 기본 온도로 만들어 넣지 않고 0점 처리한다. 사용자 추가 답변으로 상한은 **50도**로 확정했다. 50도 이상은 만점으로 제한한다. |
| 자연어 메시지 | 유사 프로젝트 제목·설명과의 단순 텍스트 유사도에 사용한다. 직군·기술·경력 조건은 직접 선택값을 기준으로 한다. 메시지에서 조건을 추론·추출하는 기능은 5단계로 둔다. |
| 유사 프로젝트 | 공개·미삭제 프로젝트를 후보로 하며, 관심 분야 35·기술 35·제목/설명 유사도 20·모집 상태 10점이다. 프로젝트 분야는 interests와 같은 데이터이므로 중복 채점하지 않는다. 모집 완료·진행 중·완료 프로젝트도 유사 사례로 포함하고 모집 상태 점수로 구분한다. |
| 기간 비교 | 프로젝트 시작일에 조건 개월 수를 더해 종료일과 비교하는 방향이다. 사용자 추가 답변으로 **계산·표시만 적용**하고 필터·점수에는 반영하지 않는다. plusMonths로 월말을 보정하고 조건 종료일과 실제 예정 종료일의 차이를 일수로 표시한다. 날짜 누락·역전·계산 불가는 비교 미확인(null)이다. 프로젝트 도메인에 개월 수 컬럼을 추가하지 않는다. |
| 정렬·개수 | 개발자·프로젝트 각각 점수 내림차순, 동점은 ID 오름차순이다. 점수는 소수 둘째 자리까지 표시한다. 각각 최대 10건이며 모집 인원만큼 반환을 제한하지 않는다. 직군별 요청 인원·필터 통과 후보 수·반환 후보 수를 제공한다. 다중 직군 후보는 결과에서 한 번만 반환하고 직군별 집계에는 중복될 수 있다. 실제 팀 배정·직군별 정원 보장은 하지 않는다. |
| 이유·후속 범위 | 3단계는 기본 추천 이유와 내부 점수 산출 근거를 만든다. 프리미엄 상세 분석·구독 확인·무료 접근 차단 API/UI는 6단계다. 결과 DB 저장·실행 API는 4단계이며 Gemini·사용량 차감도 이번 엔진 범위에 포함하지 않는다. |

- 첨부 `portfolios` ERD에는 id·user_id·title·thumbnail_url·topic·summary·description·role·tech_stack·attachments·visibility·created_at·updated_at이 있다. 설계 자료이며 실제 엔티티·DDL 적용 또는 visibility 허용값·열람 계약 확인의 증거가 아니다. 임의로 테이블·컬럼을 추가하지 않는다.
- 점수 계산 세부 기준: 직군 점수는 `일치 직군의 요청 인원 합 / 전체 요청 인원 합 × 직군 배점`이다. 기술·프로젝트 관심 분야는 정규화·중복 제거 후 `일치 개수 / 요청 개수 × 항목 배점`을 쓴다. 개발자 관심 분야는 기본 이유에만 반영하고 추가 가산점은 없다.
- 텍스트는 대소문자·유니코드·공백을 정규화하고 HTML 태그를 제거한 뒤 토큰 집합 Jaccard 유사도(교집합/합집합)를 쓴다. 메시지가 없거나 유효 토큰이 없으면 텍스트 배점을 분모에서 제외한다. 프로젝트 기술 미선택도 분모에서 제외하며 후보 데이터 누락은 0점이다. 모집 상태는 모집 중 10점·모집 완료 5점·진행 중 3점·완료/미확인 0점이다.
- 각 비율은 소수 12자리로 계산하며 합산 후 100점 환산·HALF_UP 소수 둘째 자리 반올림한다. 최종 표시 점수로 정렬한 뒤 동점 ID 오름차순을 적용한다. 항목별 점수는 환산 전 배점 기준이며 경험은 UNASSESSED, 미선택 조건은 NOT_REQUESTED로 구분한다.
- `ai.recommendation` 설정으로 직군·기술·경험·신뢰 온도 및 프로젝트 항목 배점과 신뢰 온도 상한을 조정할 수 있다. 모집 상태별 비율·결과 상한·조회 배치 크기는 AI 전용 상수다. 명시적 직군 코드/label과 기술 별칭(React.js/ReactJS, NodeJS, NextJS, SpringBoot, Postgres)만 대응시키며 자유 입력값은 정규화한 정확 일치로 비교한다.
- 후보가 없으면 빈 결과와 안내를 반환한다. 후보 조회는 ID 오름차순 200건씩 수행하며 각 배치에서 상위 10건을 유지하므로 첫 배치 이후 고득점 후보도 평가한다. 공개 필터는 ACTIVE·비어 있지 않은 tag·직군이 있는 회원, 공개·미삭제 프로젝트를 기준으로 한다. 이메일·연락처·결제·인증 정보와 상세 자기소개·포트폴리오를 후보 projection에 포함하지 않는다.

## 기존 자료와의 관계

프론트의 기존 Mock 원본·이전 결과 조회는 보존했다. 로그인 사용자의 메시지 전송은 분석 모드로 서버에 저장하고 ASSISTANT와 정형 조건을 화면에 반영한다. 추천 버튼만 sync 후 서버 추천을 실행하며, 분석은 추천·사용량을 실행하지 않는다. 비로그인 입력은 서버에 저장하지 않는다. 전송 전 입력문은 로그인 계정의 대화별 draft로 보존한다. Mock 조건 타입·점수식·관리자 예외를 서버 정책으로 확정하지 않는다. [이전 API 초안](api-plan.md)의 `/matching/...` 경로도 현재 AI 계약으로 사용하지 않는다.

현재는 로컬 H2 실행 설정과 기본/배포 PostgreSQL 설정이 함께 있다. 실제 환경·ERD·DDL 확인 상태와 필요한 팀 자료는 청사진에서 관리한다. [PostgreSQL SQL 초안](sql/ai-conversations-proposal.sql)과 테스트 H2 fixture는 실제 팀 스키마·적용 완료 증거가 아니다.

5개 테이블별 컬럼·확정 정책·권장 CHECK/UNIQUE·미확정 사항은 [API 명세의 설계 정리](ai-api-spec.md#5개-테이블-설계-정책권장-제약-2026-11-04-추가-정리)에 모았다. `current_conditions`의 NOT NULL·빈 객체 기본값, 상태 Enum 예시, rank 양수, 메시지 SET NULL 등 권장 항목을 실제 적용 완료나 확정 API 계약으로 간주하지 않는다.

### 메인 입력의 대화 전환 (2026-11-05 갱신)

- 로그인 계정의 메인 작성 중 입력은 소유 계정이 일치할 때 새로고침 시 복원한다. 추천 시작 시 새 로컬 대화와 메인 설명 초기화를 한 번에 저장하며, 저장 성공 후에만 대화 화면으로 이동한다. 실패하면 입력·기존 대화를 유지하고 재시도한다.
- 제출 중 버튼 잠금과 최신 메인 입력 확인으로 연속 제출을 막는다. 같은 문장을 새로 작성해 별도 대화를 만드는 것은 허용한다. 기존 중복 기록은 자동 삭제/병합하지 않으며 목록에서 직접 삭제한다.
- 이전 추천 대화 열기도 로그인이 필요하며 guest 초안 인계는 제거했다. 서버 API·추천 실행·사용량 정책 변경은 없다.

### 2단계 조건 관리 현재 정책 (2026-11-05)

최신 사용자 요청으로 별도 프로젝트 분야 입력(fields)을 제거하고 interests로 통합한다. 기존 5개와 삭제할 분야 선택지를 함께 사용한다는 사용자 답변을 반영했다. 종전 분야 직접 입력·직군 Enum 한정·선택 조건까지 필수로 안내하던 프론트 정책을 대체한다.

| 항목 | 현재 정책 |
|---|---|
| 관심 분야(프로젝트 분야) | 필수, 복수 선택. 생산성·핀테크·교육·커뮤니티·AI·웹·모바일·AI / 머신러닝·데이터·게임·보안·클라우드 / 인프라 총 12개 |
| 기술 스택 | 선택, 기존 버튼 선택+직접 입력/추가·삭제. 직접 추가한 기술 태그는 기본 선택 버튼 아래·직접 입력창 위에 표시. 최대 30개·각 50자, 빈 값/중복 차단·알려진 기술 표기 정규화. 서버 기존 계약 유지 |
| 모집 직군·인원 | 선택/직접 입력 허용. 직군 최대 12개·이름 1~30자·인원 1~20명 정수, 같은 이름 중복 금지 |
| 요구 경력 | 필수. 경력 무관·1년 이상·2년 이상·3년 이상·5년 이상 |
| 예상 기간 | 필수. 조건은 개월 수. 기존 화면의 1·2·3·6·12개월 선택지, 서버의 1~36개월 유효 범위 유지 |
| 프로젝트 설명 | 선택. 메시지 입력과 별개인 로컬 조건 설명이며 조건 PUT에 보내지 않음 |

- 서버 PUT은 interests·career·durationMonths를 필수로 전체 교체한다. 기술·직군 미선택을 허용하며 선택 조건을 지우려면 세 필수값만 전송한다. {} PUT은 400이다. 프론트 준비 상태/추천 버튼 검증도 필수 세 항목만 요구한다. 필수 이름 옆에 빨간색 (필수)를 표시한다. 추천 클릭 시 빠진 항목만 안내하고 첫 누락 입력으로 스크롤·포커스를 이동한다. 값을 채우면 누락 안내도 갱신한다.
- 공통 Interest·JobCategory·ProjectJobRole은 수정하지 않는다. AI 전용 통합 분야 목록과 자유 입력 직군을 회원·프로젝트 데이터에 자동 등록하지 않는다.
- 이전 서버 JSON은 재검증·일괄 변경하지 않고 조회를 유지한다. 다음 PUT은 fields를 받지 않는다. 로컬에서는 이전 분야 기본 선택을 관심 분야로 이동하며 과거 자유 입력·메시지/결과는 호환 데이터로 보존한다.
- 추천 조건은 개월 수를 쓰고, 실제 프로젝트는 기존 시작·종료 예정일을 유지한다. 2단계에서는 기간 비교를 구현하지 않았으며 현재 3단계 비교 정책은 위 추천 엔진 절을 따른다. 프로젝트 담당 코드는 변경하지 않는다.
- 2단계 당시에는 로그인 필수·계정별 로컬 보존·본인 조건 비공개만 보완했다. 이후 AI BFF/서버 동기화·추천 실행 연결은 아래 2026-11-07 범위로 구현했으며 Gemini·사용량은 추가하지 않는다.

요청/응답과 입력 검증은 [2단계 API 계약](ai-api-spec.md#2단계-구현-api--조건-전체-교체-2026-11-05)을 따른다. 과거 정책·테스트 실행은 [진행 현황](ai-progress.md)에 당시 기록으로 보존한다.

### 4단계 백엔드 실행·저장 정책 (2026-11-06)

- 동기 실행하며 저장 조건을 현재 DTO로 재검증하고 요청에 스냅샷으로 보존한다. 선택 메시지는 동일 대화의 10000자 이하 USER만 허용한다. 버튼 실행은 메시지 NULL·텍스트 비교 제외다.
- 상태는 PENDING → SUCCESS/FAILED다. 후보 0건도 정상 계산이면 SUCCESS다. 결과 일부만 저장하지 않으며 저장 실패는 전체 결과 롤백 후 FAILED로 기록한다.
- 개발자·프로젝트 각각 1위부터 점수·기본 이유를 저장한다. detailed_reason은 NULL이며 상세 이유를 응답하지 않는다. GET은 저장된 ID·점수·이유·순위를 반환하며 현재 프로필을 재조회·재계산하지 않는다.
- 같은 대화·키·조건/메시지는 기존 요청을 반환한다. 같은 키로 다른 조건/메시지는 409이며 실패 후 재실행은 새 키를 사용한다. 조건 스냅샷과 메시지 ID를 직접 비교하므로 input_hash는 추가하지 않는다. 메시지 내용 수정 API는 현재 없다.
- 첨부 ERD의 analysis_level은 이번 스키마·엔티티에서 보류한다. 기본/상세 분석의 허용 값·활용 계약은 6단계에서 확정한다. status는 PostgreSQL ENUM 대신 VARCHAR(20)+CHECK로 확정했다. recommendation_type은 추가하지 않는다.
- 프로세스 종료로 남은 PENDING의 자동 복구·만료는 미구현이다. 기존 키로 재계산하지 않으며 GET으로 상태를 확인한다. 월 사용량·Gemini·프론트 연결은 이번 범위에 없다.

### 2026-11-07 프론트 연동 확정·구현

- 사용자 승인: 최초 추천 대화만 서버 저장, 이후 변경은 다음 추천 시 동기화, 실패 시 초안과 식별 키 보존, 최신 결과 기본 표시·과거 요청 선택 조회, 서버 저장 시각 표시다.

- 대화·USER 메시지·조건을 `/api/v1/ai/conversations/sync`에서 한 트랜잭션으로 저장한다. 서버 응답 유실 후에도 대화별/메시지별 clientKey UNIQUE로 중복을 막는다. 기존 단건 API는 유지한다.

- 기존 ERD에는 client_key 두 컬럼이 없었다. 필요한 계약과 영향을 먼저 안내하고 AI 테이블 두 곳에만 nullable 키와 복합 UNIQUE를 추가했다. 적용 SQL은 `docs/sql/ai-draft-sync.sql`이며 자동 스키마 갱신은 사용하지 않는다.

### 2026-11-08 추천 대화 후속 개선 (현재 정책)

### 2026-11-09 프론트 분석 오류 보완

분석 실패의 USER 저장은 정상이며 같은 메시지 키로 재시도한다. 재시도 키는 계정별 기존 로컬 저장소에 보존한다. 조건 삭제는 서버 출처 정보와 함께 UI에 반영한다. 일반 대화에는 필수 조건 목록을 강제로 붙이지 않고 실제 추천 버튼에서 검증한다. 완성된 UI 조건은 분석 전에 기존 sync로 전달한다. 부분 UI 선택을 서버에 전달하는 계약은 기존 sync의 필수값 검증 때문에 아직 지원되지 않으며 임의 기본값을 넣지 않는다. 키 미설정 503의 로컬 재실행 방법은 [API 설정 안내](ai-api-spec.md#gemini-설정무료-티어검증-경계)를 따른다.
