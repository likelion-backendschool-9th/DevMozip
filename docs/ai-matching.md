# AI 추천 공통 기능 정책

기준일: 2026-11-06. 전체 단계·현재 완료 범위·남은 요구사항은 [개발 청사진](ai-progress.md), 서버 요청/응답은 [API 명세](ai-api-spec.md)를 따른다. 이 문서는 정책을 기록하며 구현 완료를 뜻하지 않는다. 2단계 조건 저장과 3단계 추천 엔진을 구현했으며 4~7단계는 미구현이다. 프론트 AI 연결은 별도 후속 범위다.

## 대화·입력·인증

- 화면은 `/ai/matching`, 서버 기본 경로는 `/api/v1/ai`다.
- AI 추천 대화는 처음부터 로그인이 필요하다. `/ai/matching` 직접 접근과 메인의 이전 대화 링크도 비로그인은 로그인으로 연결한다.
- 비로그인은 메인 입력창에 문장을 작성할 수 있으나 컴포넌트 메모리에만 두며 localStorage·대화·메시지·조건으로 저장하지 않는다. 추천 시작은 입력 길이 검증 없이 `/login?next=%2Fai%2Fmatching`으로 이동한다. 로그인 전 입력은 인계하지 않고 로그인 후 새로 작성한다.
- guest 대화 생성·저장·초안 이어받기를 제공하지 않는다. 기존 guest 기록은 저장소에서 일괄 삭제하지 않지만 화면에 노출하거나 계정으로 인계하지 않는다. 소유자가 없는 과거 메인 입력도 복원하지 않는다.
- 로그인 사용자도 추천 전까지 계정별 로컬 대화·메시지·조건을 사용한다. 메인 입력은 소유 계정이 일치할 때만 복원한다. 로그아웃 후 로컬 변경을 차단하며 서버 영속 API의 인증·소유권 검증을 유지한다. 서버 전송은 4단계 후속 계약이다.
- 요청자의 신원은 Spring Security 인증 정보에서 얻는다. 본문·쿼리의 userId, 프론트 Mock 계정 ID로 신원을 결정하지 않는다. 익명 추천 실행은 401이다.
- 이메일 기반 JWT 인증을 AI의 `CurrentUserProvider`에 연결했다. 기본/local/운영 환경은 검증된 인증 정보의 이메일로 기존 `MemberRepository.findByEmail`을 호출해 실제 users PK를 얻는다. 익명·미인증·삭제된 사용자는 401, 정지 계정은 403이다. 명시적으로 켠 dev/test 고정 ID는 개발용이며 실제 다중 사용자 인증을 대체하지 않는다.

## 대화·메시지 저장

- 대화는 `createdAt DESC, id DESC`, 메시지는 `createdAt ASC, id ASC`로 정렬한다.
- 메시지 역할은 USER/ASSISTANT다. **1단계는 USER 저장만** 하며 임시 AI 답변·자연어 분석·조건 병합·자동 추천을 만들지 않는다.
- 대화 `type/status`는 사용하지 않는다. 한 대화에서 개발자·유사 프로젝트를 함께 추천하며 MVP의 종료/보관 상태는 없다. 실제 DB 컬럼 삭제는 별도 검토 대상이다.
- 조건은 본인만 조회·수정하며 타 사용자·관리자에게 공개하지 않는다. 공개/공유 AI 조건 API는 없다.
- 본인 대화와 그 대화의 메시지만 한 트랜잭션에서 물리 삭제한다. 추천 요청·추천 결과 테이블은 1단계 삭제 경로에서 조회·삭제하지 않는다. 월 사용량은 삭제·차감·복원하지 않는다. FK 충돌은 전체 롤백한다.
- 대화의 메시지 동반 삭제는 동작 정책이다. 현재는 서비스에서 직접 삭제하며 실제 DB의 ON DELETE CASCADE는 미확인이다. 추천 기능 도입 후 대화/메시지와 추천 이력 간 FK·삭제 처리는 해당 단계에서 확정한다. 개별 메시지 삭제 시 추천 요청의 메시지 FK는 SET NULL을 권장하되 미확정이다. 사용자 탈퇴·추천 대상 사용자/프로젝트 삭제 정책도 미확정이다.
- AI 시간 필드는 LocalDateTime이다. 앱/DB 기준 시간대는 미확정이며 아래 월 사용량의 한국 시간 규칙과 구분한다.
- 설계 문서의 시간 컬럼 표기는 DATETIME으로 통일한다. 실제 DB별 SQL 타입과 기존 DDL 변경은 별도 구현 범위다.

## 조건·추천·Gemini

| 구분 | 정책·후속 단계 방향 |
|---|---|
| 직접 조건 선택 | 2단계 서버 PUT 전체 교체 구현. 분야를 interests로 통합해 1개 이상·경력·기간 필수, 기술·직군 선택. 관심 분야는 기존 5개+분야 7개 선택지, 직군은 직접 입력 허용. 초기 대화/NULL 조회 `{}` 허용, 빈 PUT은 400, 관심 분야·기술은 복수, 직군별 인원은 1명 이상 정수. 상세 DTO·임시 허용값은 API 명세 참조. 프론트 연결은 미완료 |
| 추천 실행 | 버튼으로 명시적으로 실행. 실제 DB의 개발자·유사 프로젝트를 한 요청에서 함께 추천 |
| 계산 | 3단계 백엔드 규칙 기반 엔진, 0~100점·점수 내림차순·기본 이유. 2026-11-06 확정 정책은 아래 절 참조 |
| 기본 추천 정보 | 공개 프로필·공개 기술·허용된 기본 경험 등만 사용. 상세 포트폴리오는 사용하지 않음 |
| 결과 저장 | 4단계 요청/결과 저장·조회 분리. GET은 재계산하지 않음. 최신/과거 결과와 중복 요청 구분을 설계 |
| 요청 조건 보존 | 추천 요청의 conditions는 실행 시점의 변경 불가 스냅샷. 이후 대화 조건 변경과 분리 |
| 자연어 분석 | 5단계 Gemini가 조건 JSON·변경분·추가 질문 생성. 검증 후 기존 조건과 병합하며 사용자 직접 선택이 추론보다 우선 |
| 대상·점수의 근거 | Gemini가 후보·경력·점수를 만들어 내지 않음. 추천 대상·점수는 실제 DB와 백엔드 엔진으로 결정 |

Gemini 연결은 별도 명시적 요청을 받은 단계에서만 한다. API 키는 환경변수로 관리하고 불필요한 개인정보·상세 포트폴리오를 일반 조건 분석에 보내지 않는다. 모델·타임아웃·실패 처리·세부 병합 규칙은 5단계에서 결정한다.

### 3단계 추천 엔진 정책 (2026-11-06)

사용자가 이전 제안 중 별도 변경하지 않은 방향을 승인하고 협업·경력·반환 개수를 수정한 내용을 반영한다. 이후 사용자 구현 요청으로 백엔드 내부 엔진만 구현했다. 외부 실행 API·프론트 연결·결과 저장은 추가하지 않는다.

| 항목 | 적용 정책 |
|---|---|
| 후보·정보 범위 | 실제 DB의 공개 프로필·공개 기술·관심 분야·경력과 허용된 기본 포트폴리오 정보만 사용한다. 본인·정지 계정은 제외하고 기존 공개 조회 조건을 따른다. 상세 포트폴리오는 사용하지 않는다. |
| 모집 직군 | 직접 선택한 직군이 있으면 해당 직군만 추천하고, 미선택이면 전체 직군을 대상으로 한다. 명시적 별칭만 매핑하고 알 수 없는 자유 입력 직군은 추론하지 않는다. |
| 협업 가능 상태 | `AVAILABLE`만 후보에 포함한다. `OPEN_TO_OFFERS`·`RESTING`·`BUSY`·`UNAVAILABLE`·NULL은 제외한다. 협업 상태는 필터이며 점수를 부여하지 않는다. |
| 경력 | 필수 필터다. 경력 무관은 신입·경력 미확인도 포함해 경력으로 제외하지 않는다. `N년 차`/`N년차`와 `N년 이상`을 비교 시 숫자 N으로 정규화한다. 예: 3년 차는 3년 이상 조건을 통과한다. 신입은 0년이며, 최소 연차가 있는 경우 해석 불가·누락 경력은 조건 충족을 확인할 수 없어 제외한다. 경력 자체에는 가산점이 없다. 저장 문자열·공통 Enum을 변경하지 않는다. |
| 개발자 배점 | 직군 30·기술 30·경험 20·신뢰 온도 10을 초기 배점으로 분리 관리한다. 종전 협업 10점은 제거하고 후기는 평가에서 제외한다. |
| 경험 미산정·환산 | **포트폴리오 연동 전에는 경험 20점을 ‘미산정’으로 표시하고, 사용 가능한 평가 항목만 100점으로 환산한다.** 직군·기술을 모두 선택했다면 분모는 70점이다. 미선택 직군·기술도 분모에서 제외한다. 후보자 정보 누락은 선택 조건 미지정과 구분하여 해당 항목 0점으로 처리한다. 포트폴리오 연동 후에는 포트폴리오가 없는 후보자의 경험 가산점을 0점으로 처리한다. 참여 이력·경력을 포트폴리오 경험으로 임의 대체하지 않는다. |
| 신뢰 온도 | 기본 기준은 36.5도다. 36.5도 이하 0점, 이후 선형 증가하여 상한에서 10점으로 제한하는 방향이다. 누락값은 기본 온도로 만들어 넣지 않고 0점 처리한다. 사용자 추가 답변으로 상한은 **50도**로 확정했다. 50도 이상은 만점으로 제한한다. |
| 자연어 메시지 | 유사 프로젝트 제목·설명과의 단순 텍스트 유사도에 사용한다. 직군·기술·경력 조건은 직접 선택값을 기준으로 한다. 메시지에서 조건을 추론·추출하는 기능은 5단계로 둔다. |
| 유사 프로젝트 | 공개·미삭제 프로젝트를 후보로 하며, 관심 분야 35·기술 35·제목/설명 유사도 20·모집 상태 10점이다. 프로젝트 분야는 interests와 같은 데이터이므로 중복 채점하지 않는다. 모집 완료·진행 중·완료 프로젝트도 유사 사례로 포함하고 모집 상태 점수로 구분한다. |
| 기간 비교 | 프로젝트 시작일에 조건 개월 수를 더해 종료일과 비교하는 방향이다. 사용자 추가 답변으로 **계산·표시만 적용**하고 필터·점수에는 반영하지 않는다. plusMonths로 월말을 보정하고 조건 종료일과 실제 예정 종료일의 차이를 일수로 표시한다. 날짜 누락·역전·계산 불가는 비교 미확인(null)이다. 프로젝트 도메인에 개월 수 컬럼을 추가하지 않는다. |
| 정렬·개수 | 개발자·프로젝트 각각 점수 내림차순, 동점은 ID 오름차순이다. 점수는 소수 둘째 자리까지 표시한다. 각각 최대 10건이며 모집 인원만큼 반환을 제한하지 않는다. 직군별 요청 인원·필터 통과 후보 수·반환 후보 수를 제공한다. 다중 직군 후보는 결과에서 한 번만 반환하고 직군별 집계에는 중복될 수 있다. 실제 팀 배정·직군별 정원 보장은 하지 않는다. |
| 이유·후속 범위 | 3단계는 기본 추천 이유와 내부 점수 산출 근거를 만든다. 프리미엄 상세 분석·구독 확인·무료 접근 차단 API/UI는 6단계다. 결과 DB 저장·실행 API는 4단계이며 Gemini·사용량 차감도 이번 엔진 범위에 포함하지 않는다. |

- 첨부 `portfolios` ERD에는 id·user_id·title·thumbnail_url·topic·summary·description·role·tech_stack·attachments·visibility·created_at·updated_at이 있다. 설계 자료이며 실제 엔티티·DDL 적용 또는 visibility 허용값·열람 계약 확인의 증거가 아니다. 임의로 테이블·컬럼을 추가하지 않는다.
- 점수 계산 세부 기준: 직군 점수는 `일치 직군의 요청 인원 합 / 전체 요청 인원 합 × 직군 배점`이다. 기술·프로젝트 관심 분야는 정규화·중복 제거 후 `일치 개수 / 요청 개수 × 항목 배점`을 쓴다. 개발자 관심 분야는 기본 이유에만 반영하고 추가 가산점은 없다.
- 텍스트는 대소문자·유니코드·공백을 정규화하고 HTML 태그를 제거한 뒤 토큰 집합 Jaccard 유사도(교집합/합집합)를 쓴다. 메시지가 없거나 유효 토큰이 없으면 텍스트 배점을 분모에서 제외한다. 프로젝트 기술 미선택도 분모에서 제외하며 후보 데이터 누락은 0점이다. 모집 상태는 모집 중 10점·모집 완료 5점·진행 중 3점·완료/미확인 0점이다.
- 각 비율은 소수 12자리로 계산하며 합산 후 100점 환산·HALF_UP 소수 둘째 자리 반올림한다. 최종 표시 점수로 정렬한 뒤 동점 ID 오름차순을 적용한다. 항목별 점수는 환산 전 배점 기준이며 경험은 UNASSESSED, 미선택 조건은 NOT_REQUESTED로 구분한다.
- `ai.recommendation` 설정으로 직군·기술·경험·신뢰 온도 및 프로젝트 항목 배점과 신뢰 온도 상한을 조정할 수 있다. 모집 상태별 비율·결과 상한·조회 배치 크기는 AI 전용 상수다. 명시적 직군 코드/label과 기술 별칭(React.js/ReactJS, NodeJS, NextJS, SpringBoot, Postgres)만 대응시키며 자유 입력값은 정규화한 정확 일치로 비교한다.
- 후보가 없으면 빈 결과와 안내를 반환한다. 후보 조회는 ID 오름차순 200건씩 수행하며 각 배치에서 상위 10건을 유지하므로 첫 배치 이후 고득점 후보도 평가한다. 공개 필터는 ACTIVE·비어 있지 않은 tag·직군이 있는 회원, 공개·미삭제 프로젝트를 기준으로 한다. 이메일·연락처·결제·인증 정보와 상세 자기소개·포트폴리오를 후보 projection에 포함하지 않는다.

## 무료·프리미엄·월 사용량

| 항목 | 무료 | 프리미엄 |
|---|---|---|
| 기본 추천 | 공개 프로필·기술·기본 추천 이유·적합도 | 동일 |
| 상세 포트폴리오·상세 추천 이유 | 접근 불가 | 서버 구독·열람권 확인 후 6단계 상세 분석 |
| 월 신규 추천 한도 | 5회 | 100회 |

2026-11-04 사용자가 추가 제공한 API 표를 기준으로 무료 한도를 기존 월 15회에서 **월 5회**로 갱신했다. 프리미엄 월 100회와 성공한 신규 추천만 차감하는 정책은 유지한다. 이후 `fcd0b4c`에서 프론트 Mock 무료 한도도 15→5로 변경해 푸시했다. 2026-11-05 develop 통합에서는 기존 Mock 회귀 테스트의 기대값도 5회로 맞췄다. 실제 서버 사용량 제한은 7단계 미구현이다.

- 7단계에서 **한국 시간 매월 1일 00:00**을 기준으로 새 월 사용량을 적용한다. `(user_id, usage_month)` 유일성을 보장한다.
- 개발자·프로젝트의 새로운 추천 결과 생성 성공에만 한 요청당 1회 차감한다. 대화 생성·메시지·조건 변경·기존 결과 조회·상세 분석·추천 실패는 차감하지 않는다.
- 4단계부터 중복 요청 식별을 설계하며, 7단계에서 중복 실행/차감·동시 한도 초과를 막고 추천 상태·결과·사용량의 일관성을 검증한다.
- 요금제 변경 시 현재 요금제 한도를 적용하는 방향이다. 판정 원천·경계 시점·한도 오류·0건/부분 실패의 성공 기준은 해당 단계에서 정한다. 관리자 한도 예외는 확정하지 않았다.
- 상세 분석은 실제 포트폴리오의 확인된 사실만 사용하고 기존 분석을 재사용한다. 포트폴리오 수정·비공개 전환 시 재분석/기존 결과 노출은 미확정이다.

## 기존 자료와의 관계

프론트의 기존 Mock 원본·이전 결과 조회는 보존했다. 현재 AI 대화 전송에서는 USER만 로컬 기록하며 자동 답변·추천·차감·자연어 분석을 실행하지 않는다. 로그인 사용자의 조건 추천 버튼은 새 결과를 만들지 않고 준비 중 안내만 제공한다. 전송 전 입력문은 로그인 계정의 대화별 draft로 보존한다. Mock 조건 타입·점수식·관리자 예외를 서버 정책으로 확정하지 않는다. [이전 API 초안](api-plan.md)의 `/matching/...` 경로도 현재 AI 계약으로 사용하지 않는다.

현재는 로컬 H2 실행 설정과 기본/배포 PostgreSQL 설정이 함께 있다. 실제 환경·ERD·DDL 확인 상태와 필요한 팀 자료는 청사진에서 관리한다. [PostgreSQL SQL 초안](sql/ai-conversations-proposal.sql)과 테스트 H2 fixture는 실제 팀 스키마·적용 완료 증거가 아니다.

5개 테이블별 컬럼·확정 정책·권장 CHECK/UNIQUE·미확정 사항은 [API 명세의 설계 정리](ai-api-spec.md#5개-테이블-설계-정책권장-제약-2026-11-04-추가-정리)에 모았다. `current_conditions`의 NOT NULL·빈 객체 기본값, 상태 Enum 예시, rank 양수, 메시지 SET NULL 등 권장 항목을 실제 적용 완료나 확정 API 계약으로 간주하지 않는다.

### 메인 입력의 대화 전환 (2026-11-05 갱신)

- 로그인 계정의 메인 작성 중 입력은 소유 계정이 일치할 때 새로고침 시 복원한다. 추천 시작 시 새 로컬 대화와 메인 설명 초기화를 한 번에 저장하며, 저장 성공 후에만 대화 화면으로 이동한다. 실패하면 입력·기존 대화를 유지하고 재시도한다.
- 제출 중 버튼 잠금과 최신 메인 입력 확인으로 연속 제출을 막는다. 같은 문장을 새로 작성해 별도 대화를 만드는 것은 허용한다. 기존 중복 기록은 자동 삭제/병합하지 않으며 목록에서 직접 삭제한다.
- 이전 추천 대화 열기도 로그인이 필요하며 guest 초안 인계는 제거했다. 서버 API·추천 실행·사용량 정책 변경은 없다.

### 2단계 조건 관리 현재 정책 (2026-11-05)

최신 사용자 요청으로 별도 프로젝트 분야 입력(fields)을 제거하고 interests로 통합한다. 기존 5개와 삭제할 분야 선택지를 함께 사용한다는 사용자 답변을 반영했다. 종전 분야 직접 입력·직군 Enum 한정·선택 조건까지 필수로 안내하던 프론트 정책을 대체한다.

| 항목 | 현재 정책 |
|---|---|
| 관심 분야(프로젝트 분야) | 필수, 복수 선택. 생산성·핀테크·교육·커뮤니티·AI·웹·모바일·AI / 머신러닝·데이터·게임·보안·클라우드 / 인프라 총 12개 |
| 기술 스택 | 선택, 기존 버튼 선택+직접 입력/추가·삭제. 직접 추가한 기술 태그는 기본 선택 버튼 아래·직접 입력창 위에 표시. 최대 30개·각 50자, 빈 값/중복 차단·알려진 기술 표기 정규화. 서버 기존 계약 유지 |
| 모집 직군·인원 | 선택/직접 입력 허용. 직군 최대 12개·이름 1~30자·인원 1~20명 정수, 같은 이름 중복 금지 |
| 요구 경력 | 필수. 경력 무관·1년 이상·2년 이상·3년 이상·5년 이상 |
| 예상 기간 | 필수. 조건은 개월 수. 기존 화면의 1·2·3·6·12개월 선택지, 서버의 1~36개월 유효 범위 유지 |
| 프로젝트 설명 | 선택. 메시지 입력과 별개인 로컬 조건 설명이며 조건 PUT에 보내지 않음 |

- 서버 PUT은 interests·career·durationMonths를 필수로 전체 교체한다. 기술·직군 미선택을 허용하며 선택 조건을 지우려면 세 필수값만 전송한다. {} PUT은 400이다. 프론트 준비 상태/추천 버튼 검증도 필수 세 항목만 요구한다. 필수 이름 옆에 빨간색 (필수)를 표시한다. 추천 클릭 시 빠진 항목만 안내하고 첫 누락 입력으로 스크롤·포커스를 이동한다. 값을 채우면 누락 안내도 갱신한다.
- 공통 Interest·JobCategory·ProjectJobRole은 수정하지 않는다. AI 전용 통합 분야 목록과 자유 입력 직군을 회원·프로젝트 데이터에 자동 등록하지 않는다.
- 이전 서버 JSON은 재검증·일괄 변경하지 않고 조회를 유지한다. 다음 PUT은 fields를 받지 않는다. 로컬에서는 이전 분야 기본 선택을 관심 분야로 이동하며 과거 자유 입력·메시지/결과는 호환 데이터로 보존한다.
- 추천 조건은 개월 수를 쓰고, 실제 프로젝트는 기존 시작·종료 예정일을 유지한다. 2단계에서는 기간 비교를 구현하지 않았으며 현재 3단계 비교 정책은 위 추천 엔진 절을 따른다. 프로젝트 담당 코드는 변경하지 않는다.
- 로그인 필수·계정별 로컬 보존·본인 조건 비공개를 유지한다. AI BFF/서버 동기화·추천 실행·Gemini·사용량 기능은 추가하지 않는다.

요청/응답과 입력 검증은 [2단계 API 계약](ai-api-spec.md#2단계-구현-api--조건-전체-교체-2026-11-05)을 따른다. 과거 정책·테스트 실행은 [진행 현황](ai-progress.md)에 당시 기록으로 보존한다.
